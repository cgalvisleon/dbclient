# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`dbclient` — a VS Code extension (TypeScript) that is a database client in the style of the "Database Client" extension (`cweijan.vscode-database-client2`), with the SQL editor modeled on NetBeans' SQL editor. Engines: PostgreSQL, MySQL, SQL Server, Oracle, SQLite, Redis and NATS — all in one connections tree, each with its own editor (`.sql` editor, `.redis` editor + value viewer, NATS console). The user tests it in Cursor (VS Code 1.128 base, Node 24); there is no VS Code or `code` CLI on this machine. Git repo with `origin` at `git@github.com:cgalvisleon/dbclient.git`; MIT license. Releases: bump `version`, add a `CHANGELOG.md` section, push tag `v<version>` → `.github/workflows/release.yml` tests, packages, creates the GitHub Release and publishes to Open VSX / Marketplace when secrets `OVSX_PAT` / `VSCE_PAT` exist. Cursor installs from Open VSX, VS Code from the Marketplace (since 0.13.1; the store name is "DB Client: SQL, Redis & NATS" because "DB Client" is taken there). The `VSCE_PAT` token lives in the macOS keychain: `VSCE_PAT="$(security find-generic-password -s VSCE_PAT -w)" ./deploy.sh -m` — never print it.

## Commands

```bash
npm run typecheck          # tsc --noEmit (src + test)
npm run build              # esbuild → dist/extension.js (watch: npm run watch)
npm test                   # vitest: unit tests; integration tests skip without DBCLIENT_* vars
npm run test:integration   # same, test files one at a time (use with every fixture up)
npx vitest run test/unit/statements.test.ts -t "oracle"   # single file / test
npm run test:smoke         # builds, downloads VS Code into .vscode-test/, runs test/smoke/suite inside it
npm run package            # typecheck + production build + vsce → dbclient-<version>.vsix
npm run publish:ovsx       # package + publish to Open VSX (needs OVSX_PAT); publish:vsce → VS Code Marketplace (VSCE_PAT)
./deploy.sh -b | -d | -m  # -b: package the .vsix; -d: publish to Open VSX (OVSX_PAT); -m: to the VS Code Marketplace (VSCE_PAT); builds if missing
npm run icons              # regenerate media/icons/ from img/ (macOS: uses sips), then the colored set; media/icon.png = img/db-client.svg exported at 256 px
node scripts/build-icon-colors.mjs   # only media/icons/colors/<color>/ (hue shift of the connection icons, no sips)
```

Integration and smoke tests read `DBCLIENT_PG_*`, `DBCLIENT_MYSQL_*`, `DBCLIENT_MSSQL_*`, `DBCLIENT_ORACLE_*` (`_SERVICE`, default `FREEPDB1`), `DBCLIENT_REDIS_*` and `DBCLIENT_NATS_SERVERS`. NATS auth modes are tested against throwaway servers: `eval "$(scripts/nats-auth-fixture.sh start)"` (Docker, `nsc`/`nk` from `natsio/nats-box`, random keys) exports `DBCLIENT_NATS_AUTH_*`; `stop` removes them. Local containers usually running: `postgres` (user/db `test`), `jsql-mysql` (root), `jsql-mssql` (sa), `jsql-oracle` (APP_USER `jsql`), `redis` (password in its command line) and `nats` (no auth, JetStream on). Read passwords from `docker inspect <name>` env into the variables — never write them to files. Tests must not touch existing data: Redis tests use db 15 with a unique key prefix, NATS tests a temporary stream, SQL tests their own temp database/table. The smoke suite injects passwords by overriding `store.getSecrets`, so it never touches the macOS keychain.

## Architecture

- `src/drivers/` must never import `vscode`. `types.ts` defines `Driver` plus `SqlDriver` (`execute` returns one result per result set), `KvDriver` (`command`, `scan`) and `PubSubDriver`; a `DriverFactory` declares its form `fields` (`secret`, `showWhen`, `file` kinds), `category` (`sql`/`kv`/`pubsub`) and `dialect`. Adding an engine = new factory + one line in `registry.ts`.
- Every SQL driver keeps metadata connections separate from one dedicated session per database/schema (so `SET`, `BEGIN`, temp tables persist), caps rows at `dbclient.maxRows` while streaming, and throws `StatementError` with `position` (1-based char) or `line` (1-based) inside the statement; `sqlRunner` maps either to a diagnostic. Engine quirks worth knowing: MySQL truncation sends `KILL QUERY` and waits for it before releasing the session; MSSQL must use `request.batch()` (not `query`) for session state; Oracle needs the trailing `;` re-added to PL/SQL blocks and can connect by `jdbcUrl` (`connectBy`; `drivers/oracleUrl.ts` turns it into Easy Connect or a descriptor, and `sshTunnel.ts` rewrites it for the tunnel); SQLite uses `node:sqlite` (absent before Node 22.13).
- `editor/statements.ts` splits per dialect (`GO` for mssql, `DELIMITER` and BEGIN…END bodies for mysql, `/` lines and PL/SQL blocks for oracle, triggers for sqlite, `$$` for postgres) and returns offsets into the document.
- `src/store/connectionStore.ts` — user-level `connections.json` in `globalStorageUri` holding `connections` and nested `folders` (`parentId`; a connection's `folderId`); deleting a folder moves its content up a level, moves refuse cycles, items pointing at a missing folder show at the top level. Secrets in SecretStorage as `dbclient.<id>.<field>`. `exportData`/`importData` (+ `parseExport`) back Export/Import Connections (all, one folder, or selected connections without folders; import may target a folder, merge only): never secrets (secret option keys are stripped on both sides), ids kept when free so a restored backup finds its secrets and SQL files; merge never overwrites (identical → skipped, conflicts → renamed copies), replace deletes what is not in the file (the extension then removes their SQL files and history).
- SQL locations: a SQL connection may also have `sqlLocations` (linked folders) and `sqlSaveLocation`, stored as typed (`~`, `${workspaceFolder}` expanded at use, see `src/store/sqlLocations.ts`). `src/connections/sqlLocations.ts` resolves them, watches linked folders (`FolderWatcher`) and answers which connection owns a file: the most specific location wins, ties make `DocumentBindings.pick()` ask once and remember. The tree shows one `SqlLocationItem` per location (internal "Saved", linked, external save) with `SqlDirItem` subfolders (`listDir` skips hidden/dependency folders, 1000 entries max). Never delete files outside the internal folder: unlinking only edits the config, and deleting a connection only removes its internal folder.
- `src/store/sqlFiles.ts` keeps saved `.sql` files at `<root>/<connectionId>/*.sql` (root = `dbclient.sqlFolder` or `globalStorage/sql`). The folder implies the connection: `DocumentBindings` falls back to it when a file has no explicit binding. The tree shows a `SqlFolderItem` ("SQL") first under every SQL connection, even when offline; deleting a connection deletes its files.
- Excel export: `src/export/xlsx.ts` is a dependency-free `.xlsx` writer (ZIP + SpreadsheetML). It writes numeric-typed columns as numbers only when no precision is lost, and offset-less dates/timestamps as Excel dates. That is why the Postgres driver keeps date/time types as server text instead of JS Dates.
- Table metadata: `SqlDriver` also has `catalog(database)` (tables/views + default schema), `describe(ref)` (columns, PK in key order, indexes; unqualified/lower-case names resolve like the engine), `ddl(ref)` and `transaction(database, statements)` (parameterized, on a connection of its own, rolls back unless each statement hits `expect` rows; MySQL uses `FOUND_ROWS` so unchanged updates still count). Tree table/view nodes carry `meta.{schema,name}`. `src/sql/` is pure: `parse.ts` (tokenizer, table refs with aliases, single-table SELECT, completion context), `identifiers.ts` (quoting/placeholders per dialect), `generate.ts` (templates, structure, CREATE TABLE, grid DML), `editable.ts`. `connections/catalog.ts` caches catalog/describe per connection (cleared on disconnect, Refresh and DDL statements); completion only queries it while the connection is open.
- Grid editing: `SqlRunner` asks `GridEditor.prepare` for each single-result SELECT; editable tabs carry `edit {id, columns, key}` (else `readOnly` reason). `media/results.js` keeps pending changes per tab and posts `commit` with values by result-column index; `GridEditor` maps them to table columns, runs `gridStatements` through `driver.transaction`, re-runs the query and answers `committed`. Drivers that read dates as JS Dates (mssql, oracle) get ISO strings back as Dates for temporal columns (`drivers/params.ts`). `test/unit/resultsWebview.test.ts` drives the real webview script in jsdom.
- Query history: `src/store/queryHistory.ts` appends one JSON line per executed statement/Redis command to `globalStorage/history/<connectionId>.jsonl` (compacted past 1.5× `dbclient.historySize`; 0 disables; Redis `AUTH`/`HELLO`/`ACL`/`MIGRATE`/`CONFIG` never recorded). `SqlRunner`/`RedisRunner` record; `editor/historyPicker.ts` (**Query History…**) inserts into the active editor when it is bound to the same connection, else opens a new bound editor. Deleting a connection clears its history.
- Refresh and drop: `dbclient.refreshNode` re-reads one connection/node (`ConnectionsTree.refreshItem`; drivers do not cache children) and clears its catalog cache; `SqlRunner` calls `manager.contentChangedOf(id)` once after a run that had DDL. `dbclient.drop` (`TableActions.drop`) builds `dropSql` (`src/sql/generate.ts`: tables/views everywhere, Postgres materialized views via `meta.materialized`, schemas = Postgres/MSSQL schemas, MySQL databases, Oracle users; `canCascade`) and runs it through `driver.transaction`. Tree node contextValue is `<kind> <category> <dialect>`, so menus can target one engine (MySQL `database` nodes get **Drop…**).
- The tree's `FolderItem` (contextValue `connectionFolder`) is a user folder — different from driver nodes of kind `folder` (Tables, Views…). `ConnectionsDragAndDrop` moves connections/folders; the form's Folder select must be kept when saving, or edits would drop the folder.
- `src/connections/manager.ts` holds live drivers. `onDidChangeState` (connect/disconnect) refreshes the whole tree; `onDidChangeContent` (driver-side, e.g. NATS subscriptions, throttled) refreshes only that connection's subtree.
- `editor/bindings.ts` maps a `.sql` or `.redis` document to `{connectionId, database}` (`EDITOR_CATEGORIES`: sql→sql, redis→kv). `dbclient.run`/`runFile` dispatch on the editor language; `dbclient.newQuery` opens a SQL or Redis editor, or the NATS console for pub/sub connections.
- Network security: `drivers/tls.ts` (`sslFields`, `tlsOptions`: `disable`/`require`/`verify-full`, PEM files, `sslPassphrase` secret; MSSQL keeps its `encrypt`/`trustServerCertificate` fields plus `sslCa`; Oracle thin reads CA+cert+key as one PEM wallet, so a CA alone is rejected) and `drivers/sshTunnel.ts` (`sshFields`; `connectDriver` opens an `ssh2` local forward and points the driver at `127.0.0.1:<port>`, with `options.tlsServername` keeping certificate checks on the real host; the driver's `disconnect` closes the tunnel; `ConnectionManager.connect`/`test` go through it). Form fields carry `section` (headings in the form); `showWhen` on a field missing from saved options uses its default. `DriverFactory.prepare` normalizes form values before Test/Save and the form shows the result (Oracle moves URL credentials into `user` and the password secret). esbuild marks `cpu-features` and `*.node` external so ssh2 runs on its pure-JS fallback — never ship native modules.
- Localization: every user-visible string goes through `vscode.l10n.t('literal')` (code), `t('literal')` (webviews; `media/l10n.js` reads the bundle `webviewHtml` injects) or `%key%` (`package.json` → `package.nls.json`). Driver field labels/hints/placeholders/sections/choices and `tree/words.ts` are translated where they are shown. `test/unit/l10n.test.ts` fails when `l10n/bundle.l10n.es.json` or `package.nls.es.json` misses or keeps stale keys; add the Spanish text with every new string.
- Test fixtures: `scripts/{nats-auth,tls,ssh}-fixture.sh start|stop` (Docker, random secrets, export `DBCLIENT_*`). Docker on this machine has ~4 GB and `jsql-oracle` + `jsql-mssql` use most of it: an uncapped extra MySQL got `jsql-mssql` OOM-killed, so fixtures cap memory; with every fixture up run `npm run test:integration` (files sequentially) — in parallel Oracle/MSSQL tests time out.
- Webviews are plain JS/CSS in `media/` (no bundler) behind a nonce CSP (`webviews/html.ts`): connection form, results panel (bottom `WebviewView`, messages queued until `ready`), Redis value viewer (`redisValue.ts` turns edits into commands), NATS console (messages buffered per connection while connected), Settings and About panel (`settings.ts`: storage paths, `dbclient.*` values, environment, GitHub links from `package.json` `repository`; it only opens the paths/links it sent).
- Icons: `src/icons.ts` returns `{light, dark}` PNGs from `media/icons/` (generated from `img/`). Connections may set `icon` (`CONNECTION_SHAPES`) and `color` (`CONNECTION_COLORS`, blue = the original set) in the form's Appearance section; `connectionIconPath` (mirrored in `media/connectionForm.js`) maps them to `media/icons/colors/<color>/…`; connection folders have a `color` too (**Change Color…**, `folderIcon` → colored `explorer.png`), built by `scripts/build-icon-colors.mjs` — keep its `COLORS`/`COLOR_ICONS` in sync (`test/unit/appearance.test.ts` checks every file exists). Webview CSP allows `img-src` from the extension; the activity-bar icon stays the monochrome `media/database.svg` because VS Code masks it.

## Documentation workflow

- `README.md` (English) is the user-facing doc and ships in the `.vsix` (it is the store page); `README.es.md` is its Spanish translation. Keep them in sync section by section: Open VSX/license badges and a one-line summary under the title, installation first, then short paragraphs, the features table and usage examples. When a feature lands or changes, update the features table and examples in both.
- Screenshots/GIFs go in `img/screenshots/` (not packaged) and are referenced by absolute `raw.githubusercontent.com/.../main/img/screenshots/…` URLs so they render on Open VSX and the Marketplace. Until they exist, both READMEs keep them as HTML comments (`<!-- GIF (…) -->`) at the spot where each goes; uncomment when the file is committed.
- `feature.md` is the user's feature definition (Spanish). When complementing it, append plain bullets in the same style — don't restructure or reformat it.
- `spec.md` holds the requirements (ID, weight in points, status 0 / 0.5 / 1), the gap formula `brecha = (total − avance) / total`, and a history table.
- After every change to the project, update `spec.md`: requirement statuses, the per-block table, the current gap %, and a new history row. Mark a requirement 1 only when it is verified; partial or unverified pieces are 0.5 with the reason.
